## Current assurance plumbing (not the product assurance capability)

- `POST /v1/tasks/{task_id}/assurance` accepts a text output only after
  Intent Record approval, persists the output and versioned report, and
  applies supported deterministic checks.
- Supported verification methods are `contains_text:<literal>`,
  `section_present:<Markdown heading>`, and `valid_json`. Unknown methods
  require human review rather than passing by default.
- Critical mandatory requirements are surfaced as hard gates. The report
  explicitly limits `all_checks_passed` to the checks performed; it does not
  assert semantic or factual correctness.
- Outputs and reports are persisted by migration
  `0003_assurance_reports.py`.
- This is not independent semantic verification. Claim extraction, source
  verification, provider execution, and correction remain unimplemented.

## Current implementation gate: evaluation readiness

- The development evaluation set has 20 synthetic cases in six domains, but
  it is not human-adjudicated and is not a holdout set.
- The evaluation runner reports exact structured-field matches and strict
  normalized-text requirement/ambiguity metrics, with domain and difficulty
  breakdowns. These are diagnostics, not semantic quality scores.
- Each report records provider, model, adapter, and prompt versions and includes
  extraction failures and release-readiness blockers.
- Release benchmarking is blocked until the holdout split, adjudication and
  reviewer roles, expected acceptance criteria, failure-mode coverage, and
  source records for citation-trap cases are complete.
- Legal cases remain excluded until reliable authoritative sources and
  qualified legal reviewers are available.

## Domain architecture decision

- Do not build a separate provider adapter for each industry. Provider
  adapters normalize access to AI providers; start with one provider behind
  the provider-neutral interface.
- Keep one general core and add optional domain assurance modules only when a
  task needs distinct acceptance criteria, reference sources, checks, or
  expertise. A module should declare supported tasks, inputs, checks, outputs,
  and version. Unsupported or inapplicable checks must be reported as
  unavailable, never silently passed.
- Validate the core and its measurement gates with one initial domain, then
  add a thin second domain and measure what is configuration versus new core
  code. Use that evidence to decide whether additional domain modules are
  warranted; do not assume the universal core generalizes or requires heavy
  domain-specific configuration. This is rules-and-checks extensibility, not
  industry-specific model training.
